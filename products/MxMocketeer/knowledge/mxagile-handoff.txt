# MxMocketeer → Development / MxAgile Handoff

## Handoff Principle
The HTML file is a two-layer artifact:
1. Visible clickable prototype for Product Owners and key users.
2. Embedded Design Contract for analysis and development agents.

## Target Mapping
- Requirements → canonical requirements
- Decisions/Rationale → decision records
- Business Rules/Calculations → specifications and acceptance criteria
- Roles/Permissions → role contract and positive/negative authorization tests
- Screens/Flows/States → UI/process specifications and Playwright scenarios
- Assumptions/Open Questions/Conflicts → refinement backlog and gates
- Out of Scope/Phase 2 → scope guard
- Mendix Candidates → technical discovery — not automatic adoption
- Business Flows (structured) → Knowledge Graph FLOW-NNN nodes (see below)

## Business Flow Handoff

When the Design Contract contains structured flows (steps[], FLOW-NNN IDs, FLOWSTEP-NNN):

1. The downstream MxAgile pipeline builds Knowledge Graph edges from the flow data:
   - step.req_refs[] → PARTICIPATES_IN edges: REQ-NNN → FLOW-NNN
   - step.screen_ref → SHOWN_ON edges: FLOW-NNN → PAGE-NNN
   - step.decision_refs[] → DECIDED_BY edges: FLOW-NNN → DEC-NNN

2. Target mapping for structured flows:
   - flows[].req_refs[] → confirm TC-NNN (test contract) exists for each REQ-NNN
   - flows[].steps[].transitions → business-level scenario paths in Playwright acceptance campaigns
   - flows[].error_paths → error state test scenarios (data_state: error in proof points)
   - FLOW-NNN stable IDs → referenced in test-contract traceability.design_contract_elements[]

3. Flow revision impact: when a new mockup revision changes step req_refs or screen_ref,
   the developer must run affected(FLOW-NNN) to surface downstream TC-NNN and VPL-NNN
   that are transitively impacted. TC-NNN where staleness_cause: DESIGN_CONTRACT_CHANGED.

4. Mermaid diagrams in the delivered HTML are generated from structured steps.
   They are not canonical. The structured steps[] in the Design Contract are canonical.
   If Mermaid and steps[] disagree: the steps[] data is correct.

## Knowledge Graph Handoff

When the Design Contract is accepted, the downstream MxAgile project's Knowledge Graph
should be refreshed to incorporate the new Design Contract data:

  1. Run: build_artifact_index.py (or graph build() operation) to pick up new artifacts.
  2. Verify graph status() returns current after the build.
  3. Use affected(DC-MOCKUP-ID) to surface all canonical artifacts downstream of this contract.
  4. For each new REQ-NNN created from the Design Contract, verify PARTICIPATES_IN edges
     exist for any flows that reference the requirement.

The Design Contract's design_contract_ref in downstream TCs must match:
  <mockup.id>@revision=<mockup.revision>
This ensures graph staleness detection works correctly when a new mockup revision arrives.

## Conflict Rule
The visible mockup shows observable behavior; the Design Contract explains intent. When there is a discrepancy, do not resolve it yourself — mark it as a conflict and ask the Product Owner.

## Handoff Readiness
- Central flows are clickable
- Relevant roles and constraints are documented
- Key states are visible or described
- Confirmed decisions are traceable
- Critical assumptions and open questions are marked
- Stable IDs and traceability are present
- Preservation Check passed

## Do Not Automatically Adopt
Unconfirmed technical candidates, sample data, temporary text, visual placeholders, and assumptions must not be treated as confirmed implementation requirements.

## Maturity and Readiness in Handoff

When a Design Contract includes an `assessment` block, MxAgile should:

1. **Read `development_handoff_readiness`** as upstream evidence quality:
   - `HANDOFF_READY` → proceed with stronger confidence; fewer expected gaps
   - `REFINEMENT_REQUIRED` → import known content; route unresolved gaps to Refinement
   - `PROTOTYPE_READY` → import available content; expect significant Discovery work
   - `BLOCKED` → surface blockers explicitly; do not proceed past Discovery until resolved

2. **Map unresolved gaps** from `assessment.gaps` to MxAgile refinement concepts:
   - `MISSING_BUSINESS_RULE` → Refinement open question / DECISION REQUIRED
   - `SECURITY_UNCLEAR` / `INCOMPLETE_DATA_SCOPE` → security/role refinement input
   - `UNTESTABLE_REQUIREMENT` → Testability concern in Test Contract derivation
   - `CONFLICT` → source conflict requiring DECISION REQUIRED
   - `INCOMPLETE_ROLE_CAPABILITY` → role contract gap; may affect negative proof points
   - Minor visual or cosmetic gaps → do not automatically block Testability Gate

3. **Preserve gap provenance** — record the original `gap_ref` (e.g., GAP-001) in the
   story specification DECISION REQUIRED entry so the gap is traceable to the mockup.

4. **Maturity is upstream evidence, not authority.** `HANDOFF_READY` means the upstream
   design is well-explored. It does NOT bypass MxAgile Discovery, gate-to-refinement,
   or any other lifecycle gate. MxAgile gates remain the authoritative decision point
   for development lifecycle progression.

5. **Legacy contracts without `assessment`** — treat as unassessed input. Apply standard
   Design Contract intake rules. Do not interpret missing maturity metadata as HANDOFF_READY.

6. **Later revision reconciliation** — when a new mockup revision arrives:
   - Re-run design-contract-intake with the new `mockup.revision`
   - Compare gap states: OPEN → RESOLVED gaps may close story-spec open questions
   - New or reopened gaps → mark affected Requirements/Test Contracts IMPACTED per staleness policy
   - Do not reset unrelated confirmed MxAgile work

## End-to-End Flow Reference

IDEA → EARLY MOCKUP (PROTOTYPE_READY) → ASSESSMENT → GUIDED INTERVIEW
→ REVISION → RE-ASSESSMENT → HANDOFF_READY → MXAGILE DISCOVERY
→ REFINEMENT → TESTABILITY GATE → IMPLEMENTATION → VERIFICATION → ACCEPTANCE

A beautiful prototype is not automatically development-ready.
An honest REFINEMENT_REQUIRED state is more valuable than a premature HANDOFF_READY claim.

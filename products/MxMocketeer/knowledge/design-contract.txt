# MxMocketeer Design Contract v1

## Purpose
The Design Contract preserves confirmed customer and design intent in the same HTML file as the clickable prototype. It is a business handoff medium, not a technical Mendix specification.

## Mandatory HTML Structure
```html
<!--
MXMOCKETEER DESIGN CONTRACT
Contract-Version: 1
Visible prototype = customer-facing UI.
#mocketeer-spec = machine-readable design context, not technical implementation.
Preserve stable IDs and unrelated confirmed knowledge during refinement.
-->
<script type="application/json" id="mocketeer-spec">{ ... }</script>
```

## Top-Level Structure
```json
{
  "schema_version": "1.1",
  "mockup": {
    "id": "MOCKUP-EXAMPLE",
    "revision": 2,
    "previous_revision": 1,
    "lifecycle_status": "REFINED_TARGET",
    "refinement_status": "PROPOSED",
    "active_target": false,
    "title": "Example",
    "language": "en",
    "updated_at": "YYYY-MM-DD",
    "change_scope": "Removed login screen — platform-module boundary. Role model preserved."
  },
  "revision_history": [],
  "revision_delta": {},
  "preservation": {},
  "project": {},
  "sources": [],
  "roles": [],
  "requirements": [],
  "decisions": [],
  "business_rules": [],
  "calculations": [],
  "data_semantics": [],
  "screens": [],
  "flows": [],
  "platform_boundaries": [],
  "role_coverage": [],
  "permissions": [],
  "assumptions": [],
  "open_questions": [],
  "conflicts": [],
  "risks": [],
  "accepted_risks": [],
  "out_of_scope": [],
  "phase2": [],
  "dependencies": [],
  "mendix_candidates": {},
  "findings": [],
  "traceability": []
}
```

`schema_version: "1.1"` adds: `lifecycle_status`, `refinement_status`, `active_target`, structured `change_scope`, `revision_history`, `revision_delta`, `preservation`, `platform_boundaries`, `role_coverage`, and `effects` on screens/states. Existing `schema_version: "1.0"` contracts remain valid and are read as-is.

## Common Fields
Where applicable, entries use:
- `id`: stable and unique, e.g. REQ-001, DEC-001, ROLE-ADMIN, BR-001, SCREEN-001.
- `status`: CONFIRMED_BY_SOURCE, CONFIRMED_BY_STAKEHOLDER, DERIVED, RECOMMENDATION, ASSUMPTION_REQUIRES_APPROVAL, CONFLICTING, OPEN, ACCEPTED_RISK, REJECTED, or SUPERSEDED.
- `source_refs`: IDs or descriptions of the source material.
- `owner`: responsible role, not necessarily a person's name.
- `scope_refs`: affected screens/flows/requirements.

## Roles and Personas
```json
{
  "id": "ROLE-MANAGER",
  "name": "Site Manager",
  "goals": [],
  "responsibilities": [],
  "organizational_scope": "all",
  "data_scope": "all application-relevant data",
  "can": ["CAP-SITE-MANAGE"],
  "cannot": ["CAP-TECHNICAL-DIAGNOSTICS"],
  "known_states": ["normal", "empty", "error"],
  "status": "CONFIRMED_BY_STAKEHOLDER"
}
```
`cannot[]` contains only explicitly excluded capabilities. Unmentioned actions are unknown — not automatically forbidden.

```json
  "business_rule_refs": [],
  "priority": "Must",
  "status": "CONFIRMED_BY_STAKEHOLDER"
}
```

## Decisions
```json
{
  "id": "DEC-001",

  "rationale": "The list overview stays visible and provides context.",

  "owner": "Product Owner"

```

## Business Rules and Calculations
Business rules are business-verifiable rules. Calculations include meaning, formula or pseudo-logic, unit, rounding, data source, and scope. Never invent a formula.

## Screens, Flows, and States
Screens contain: purpose, roles, relevant elements, requirements/decisions, states, and responsive intent. Flows contain: start, steps, alternatives, result, and error paths. States at minimum where relevant: loading, empty, normal, warning, error, success, disabled, read_only, no_permission.

## Platform Boundaries
```json
{
  "platform_boundaries": [
    {
      "id": "PLATFORM-AUTH-001",
      "provider": "AUTH_PLATFORM",
      "responsibilities": ["authentication", "sign-in", "password-management"],
      "mockup_behavior": [
        "no productive login screen",
        "demo role switcher is test-only mechanism"
      ],
      "parity_rule": "EXCLUDE_FROM_UI_PARITY",
      "implementation_rule": "REUSE_PLATFORM_MODULE",
      "role_source_rule": "Business roles remain independently relevant regardless of platform authentication",
      "modification_rule": "DO_NOT_MODIFY_PLATFORM_MODULE",
      "excluded_screens": ["SCREEN-LOGIN"],
      "decision_ref": "DEC-001",
      "status": "CONFIRMED"
    }
  ]
}
```
Platform boundaries declare which functions are delivered by platform modules (e.g. an authentication platform module) rather than the application. Excluded screens are not fachliche pages and must not generate REQ-NNN, SPEC-NNN, or implementation tasks. The role model is independent of platform boundaries.

## Role Coverage
```json
{
  "role_coverage": [
    {
      "role_id": "ROLE-E4-EINTRAGUNG",
      "role_name": "E4 Eintragung",
      "contract_present": true,
      "runtime_present": true,
      "demo_mode_present": true,
      "representative_scope_present": false,
      "required_scope": "team",
      "status": "COVERAGE_GAP",
      "gap_description": "Role defined but no representative Team scope context in demo mode."
    }
  ]
}
```
Role coverage tracks whether every fachliche role is representable and testable. A missing demo identity or scope is a `COVERAGE_GAP`, not an infrastructure gap.

## Permissions
Permissions can express cross-role rules:
```json
{
  "id": "PERM-001",
  "role_ref": "ROLE-MANAGER",
  "capability": "CAP-SITE-MANAGE",
  "effect": "ALLOW",
  "scope": "all sites",
  "explicit": true,
  "source_refs": ["SRC-001"]
}
```

## Assumptions, Questions, Conflicts, and Risks
Each entry includes: reason, owner, affected scope, and `blocks_implementation`. Assumptions are never presented as confirmed. Risks may become ACCEPTED_RISK when owner and consequence are documented.

## Mendix Candidates
Candidates only — never unconfirmed technical fact. Possible categories: modules, entities, attributes, associations, enumerations, pages, roles, microflows, integrations. Microflow types may be proposed as ACT, SUB, VAL, DS, SE, or NAV. Each candidate carries status confirmed|derived|open and a reason.

## Traceability

```json
  "role_refs": ["ROLE-MANAGER"],
  "business_rule_refs": []
}
```

## Contract Migration (v1.0 → v1.1)

`schema_version: "1.0"` contracts are valid as-is and are read without modification. When the author explicitly requests an upgrade, or when a new refinement is produced, the contract should be migrated to v1.1.

### Migration Object

Add a `migration` object at the top level to record the upgrade:
```json
{
  "migration": {
    "from_schema_version": "1.0",
    "migrated_at": "YYYY-MM-DD",
    "migrated_by": "MxMocketeer",
    "migration_notes": "Upgraded to v1.1: lifecycle fields, revision ledger, platform boundaries, role coverage added with SOURCE defaults.",
    "migrated_fields": [
      "mockup.lifecycle_status",
      "mockup.refinement_status",
      "mockup.active_target",
      "mockup.change_scope",
      "revision_history",
      "revision_delta",
      "preservation",
      "platform_boundaries",
      "role_coverage"
    ]
  }
}
```

### Default Values When Migrating from v1.0

| Field | Default on Migration | Reason |
|---|---|---|
| `mockup.lifecycle_status` | `"SOURCE"` | First known revision — founding source |
| `mockup.refinement_status` | `"ACCEPTED"` | Source is accepted by definition |
| `mockup.active_target` | `true` | Only revision — is the active target |
| `mockup.change_scope` | `""` | No prior revision to compare against |
| `mockup.previous_revision` | `null` | No predecessor known |
| `revision_history` | `[]` | No prior ledger available |
| `revision_delta` | `null` | Source revision has no delta |
| `preservation` | `null` | No baseline to compare against |
| `platform_boundaries` | `[]` | To be assessed during Discovery |
| `role_coverage` | `[]` | To be assessed during Discovery |

### Migration Rules

- **Preserve all existing IDs.** No REQ-*, DEC-*, ROLE-*, SCREEN-*, FLOW-* IDs are changed or renumbered.
- **Do not remove existing fields.** All v1.0 top-level arrays (requirements, decisions, roles, screens, etc.) are carried forward unchanged.
- **schema_version upgrades to `"1.1"` only when confirmed by the author/developer.** MxMocketeer proposes; the developer confirms.
- **The migration object is omitted on freshly-created v1.1 contracts.** It is only present when an existing v1.0 contract was upgraded.

## Preservation Contract
During refinement:
- IDs remain stable.
- Unaffected CONFIRMED entries are preserved.
- Removal only on explicit request or via SUPERSEDED decision.
- `mockup.revision` is incremented; `previous_revision` references the predecessor.
- `change_scope` lists only affected IDs.
- Before output, compare before/after IDs. Unexpected loss: STOP and report.

## Privacy and Security
No secrets, tokens, real credentials, or unnecessary personal data. Mark synthetic personal examples as mock data. Include sensitive technical information only when required for a design decision and explicitly approved.

## Maturity Assessment (optional, backward-compatible)

The `assessment` block is backward-compatible optional. Older contracts without it are valid and treated as unassessed.
When present, it expresses the current design maturity state and development handoff readiness.

```json
{
  "assessment": {
    "assessed_revision": 2,
    "assessed_at": "YYYY-MM-DD",
    "assessed_by": "MxMocketeer",
    "prototype_readiness": "READY",
    "development_handoff_readiness": "REFINEMENT_REQUIRED",
    "dimensions": [
      {
        "id": "DIM-PURPOSE_SCOPE",
        "status": "SUFFICIENT",
        "notes": "Goal, actors, and MVP scope are clear"
      },
      {
        "id": "DIM-ROLES_CAPABILITIES",
        "status": "PARTIAL",
        "notes": "Manager role defined; data scope UNKNOWN for Department Manager"
      }
    ],
    "gaps": [
      {
        "id": "GAP-001",
        "dimension": "DIM-ROLES_CAPABILITIES",
        "category": "INCOMPLETE_DATA_SCOPE",
        "description": "Which records can a Department Manager see?",
        "why_it_matters": "Data scope drives entity access rules and security tests",
        "priority": "HIGH",
        "blocking": true,
        "blocks_handoff": true,
        "affected_elements": ["ROLE-DEPTMGR", "REQ-003"],
        "suggested_interview_focus": "Can a Department Manager see only their own department or all departments?",
        "resolution_state": "OPEN",
        "source_refs": ["SRC-001"]
      }
    ],
    "blocking_gaps": ["GAP-001"],
    "next_exploration_areas": [
      {"priority": 1, "topic": "Department Manager data scope", "gap_ref": "GAP-001"},
      {"priority": 2, "topic": "Calculation rule for total amount"}
    ],
    "prototype_readiness_reason": "Enough understood to discuss main workflow",
    "handoff_readiness_reason": "GAP-001 blocks handoff: data scope undetermined"
  }
}
```

### Dimension IDs

Standard dimension identifiers:
- `DIM-PURPOSE_SCOPE` — goal, actors, MVP, scope
- `DIM-FUNCTIONAL_COVERAGE` — journeys, screens, flows
- `DIM-BUSINESS_RULES` — rules, calculations, formulas
- `DIM-ROLES_CAPABILITIES` — roles, can/cannot, operations
- `DIM-DATA_SEMANTICS` — data objects, meaning, sources
- `DIM-UX_NAVIGATION` — structure, navigation, hierarchy
- `DIM-STATES_EDGE_CASES` — loading, empty, error, disabled
- `DIM-VALIDATION_ERROR_HANDLING` — required fields, error behavior
- `DIM-SECURITY_PRIVACY` — access rules, data exposure, privacy
- `DIM-ACCESSIBILITY` — keyboard, ARIA, contrast
- `DIM-NON_FUNCTIONAL` — performance, availability, languages
- `DIM-DEVELOPMENT_HANDOFF` — testability, traceability, explicit decisions

### Dimension Status Values

- `UNEXPLORED` — topic not yet examined
- `PARTIAL` — examined; material gaps remain
- `SUFFICIENT` — enough for professional development
- `STRONG` — thoroughly covered
- `BLOCKED` — cannot progress without external input
- `CONFLICTING` — contradictory information in sources

### Readiness Values

- `PROTOTYPE_READY` — enough known to produce and usefully discuss the prototype
- `REFINEMENT_REQUIRED` — known gaps that need clarification before handoff
- `HANDOFF_READY` — all critical dimensions sufficient; no blocking gaps
- `BLOCKED` — material uncertainty prevents meaningful progress

A contract may be `prototype_readiness: PROTOTYPE_READY` while
`development_handoff_readiness: REFINEMENT_REQUIRED`. This is expected and correct.

### Gap Categories

`MISSING_INFORMATION`, `AMBIGUITY`, `CONFLICT`, `ASSUMPTION`,
`INCOMPLETE_ROLE_CAPABILITY`, `INCOMPLETE_DATA_SCOPE`, `MISSING_BUSINESS_RULE`,
`MISSING_EDGE_CASE`, `MISSING_VALIDATION`, `MISSING_ERROR_BEHAVIOR`,
`SECURITY_UNCLEAR`, `PRIVACY_UNCLEAR`, `ACCESSIBILITY_UNEXPLORED`,
`NON_FUNCTIONAL_UNEXPLORED`, `UNTESTABLE_REQUIREMENT`, `INCONSISTENT_UI_FLOW`

### Operation-Aware Role Assessment

Role capabilities use the same operation semantics as Test Contracts:
- Operations: `READ`, `CREATE`, `UPDATE`, `DELETE`, `EXECUTE`
- Dispositions: `REQUIRED`, `EXPLICITLY_FORBIDDEN`, `UNSPECIFIED`, `UNKNOWN`
- `CANNOT UPDATE` ≠ `CANNOT READ`. Never infer from one operation to another.
- Missing permission information = `UNSPECIFIED`/`UNKNOWN` — never default to FORBIDDEN.
